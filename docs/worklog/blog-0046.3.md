## Health check shape (decision)

- **Two checks, `backup` and `restoreDrill`, not one.** The two have independent states, reasons and ages, and a monitor or the owner needs to tell "backup stale" from "drill overdue". A single `recovery` check would have to collapse both into one reason and one age.
- **The brief's "healthy" is the existing `up` status.** Every other check and the container smoke already use that vocabulary, so I did not add a seventh status.
- **Reasons are generic,** because the check name already says which subsystem: `never_run`, `last_run_failed`, `stale`, `targets_missed` (drill only). Precedence: a failed latest run first, then missed targets, then staleness.
  - `targets_missed` covers a failed drill whose first failure is `rpo_exceeded` or `rto_exceeded`. It also covers a passed drill whose recorded measurements exceed today's `recoveryTargets`.
  - A drill that failed earlier, for example on a row mismatch, is `last_run_failed`.
- **Body: status and reason, plus `ageMs` and the existing `durationMs`.** `ageMs` is milliseconds since the latest run finished. `durationMs` is the probe's own timing, kept on every configured check. Failure codes, timestamps, measurements and counts stay out; tests assert this.
- **Age runs from finish, not start.** Measured from start, a healthy daily backup would flap `stale` while its successor runs. The trade-off is that the snapshot can be up to one run's duration older than reported. It is documented with the alerting advice.
- **Drill cadence is 35 days** (`restoreDrillCadenceMs`): the runbook's monthly minimum plus slack for a drill that moves a few days. RPO is `recoveryTargets.rpoMilliseconds` (24 h).
- **Never `down` for the site.** The findings degrade the check. A read failure, for example before 0011 is applied, makes the check `down` (`unavailable` or `timeout`), but only the database takes the site down. The route keeps answering 200 for degraded.
- **The in-memory runtime reports both checks as `not_configured`.** A runtime that cannot be created reports them `down`, like its other dependent checks.
- **Container checks still pass, unchanged.** The HEALTHCHECK exits 0 on `r.ok`, and a degraded report is 200. `container-smoke.mjs` accepts `ok`/`degraded` with database `up`/`degraded`. A freshly migrated container with no recorded runs reports `degraded` (`never_run`) with database `up`, so both pass.

### 1. Blocker: Neon's `channel_binding`

- **What changed.** `backupDatabaseUrl` now accepts `channel_binding` (`disable`, `prefer` or `require`, at most once) next to `sslmode`. Every other parameter is still refused, `sslnegotiation` and `sslrootcert` included. This one function checks both the recorder's `DATABASE_URL` and the source URL of `backup:create`.
- **TLS is never weakened.** A hosted host always gets `sslmode=verify-full`, and a hosted `sslmode=disable` is still `tls_required`, with or without binding. A loopback URL without TLS cannot ask for `channel_binding=require` (`invalid_configuration`): libpq would refuse to connect, and node-postgres would ignore it.
- **libpq tools.** `runPostgresTool` passes the value on as `PGCHANNELBINDING`, so `pg_dump` enforces `require`.
- **node-postgres.**
  - The installed `pg` 8.22.0 reads `enableChannelBinding` and uses SCRAM-SHA-256-PLUS when the server offers it. `@types/pg` 8.20.0 does not declare the option, so `drillPool` builds a typed config.
  - `require` and `prefer` map to `true`. `disable` and an absent value map to `false`, the unchanged default.
  - Limitation, documented: unlike libpq's `require`, node-postgres does not itself refuse a server that offers no binding. Certificate and hostname verification still holds there. A backup's `pg_dump` enforces the binding against the same database in the same run, but the recorder relies on verify-full.
- **Tests.**
  - `backup.test.ts`: the Neon URL, each value, repeats, other parameters and loopback. `createBackup` with a Neon source gets past the URL check and stops at the key.

### 2. Should-fix: the SQL checks match the decoder

- **Checks.** Migration 0011 limits `rpo_ms` and `rto_ms` to `BETWEEN 0 AND 9007199254740991` and adds `CHECK (isfinite(started_at) AND isfinite(finished_at))`.
- **Year range.** It also checks `started_at >= '0001-01-01T00:00:00Z' AND finished_at < '10000-01-01T00:00:00Z'`. This gap is of the same kind: the decoder writes instants with `toISOString` and its ISO check accepts four-digit years only. A finite year-10000 or BC timestamp would otherwise still break the read.
- **Decoder.** Each kind's latest row is now decoded on its own. A row that breaks the rules, an infinite or out-of-range instant included, reads as `unreadableRun` for that kind only. An older run never stands in for it.
- **Chosen behaviour:**
  - **Health.** That kind's check is `down` with `unavailable`. The probe throws `OperationRunError`, which names no value, logged as `health.check.failed`. The other check still reports normally.
  - **Owner view.** That card says the record could not be read and gives a next step (finding `unavailable`), with no run details.

Both cards show as unavailable, and the failure is logged as `owner.jobs.recovery.failed` under the request's correlation id. The page creates its logger as the subscribers page does.

- **Tests.**
  - `migrations.test.ts` pins the new checks.
  - Integration, direct SQL: `infinity`, `-infinity`, a BC instant, year 10000, and `MAX_SAFE_INTEGER + 1` in both columns are refused with 23514. `MAX_SAFE_INTEGER` itself is kept and read back exactly.

### 3. Should-fix: bounded recovery reads

- **One read per request.** `healthProbesFor` builds the probes of one request. The `backup` and `restoreDrill` probes share one `latest()` read, which is aborted once both probes' signals have aborted. `healthProbesFor` takes an optional store, beside its `clock`, for tests.
- **Bounded read.**
  - `PostgresOperationRunStore.latest(signal?)` takes one pooled connection. It sends `SET LOCAL statement_timeout = '1000ms'` and the select as one simple-protocol message. They share an implicit transaction, so the limit applies to this read only, in one round trip.
  - A client-side deadline of 1.5 s (`latestRunsTimeoutMs`) covers getting a connection and running the statement. A connection that arrives too late goes back to the pool unused. A statement still running has its connection closed (`release(true)`).
  - On the deadline, or on PostgreSQL's `57014`, the read rejects with a `TimeoutError`. A caller's abort ends it the same way, with the caller's reason.
- **Health.** A probe that rejects with a `TimeoutError`, meaning it hit its own deadline shorter than the check's, is now `down` with `timeout` and logged as `health.check.timeout`. A stalled database therefore reads as `timeout` on both checks, not `unavailable`.
- **Tests.**
  - Stalled store, as the brief asks: the store never settles. Both checks report `timeout` at 2 s, `latest()` is called once, and its signal aborts only after both probes have.
  - Stalled statement: both checks report `timeout` at 1.5 s, one read is issued, and its connection is closed.
  - Store: a stalled connection request (the late connection is released unused), a stalled statement, a caller abort, an already-aborted caller (no connection requested), `57014` and other errors.
  - Health: the `TimeoutError` mapping.
  - Integration: another session holds an `ACCESS EXCLUSIVE` lock on `operation_runs`. The read rejects with a `TimeoutError` inside the health limit, both checks report `timeout` and the database stays `up`. No lock waiter is left while the lock is still held, which shows PostgreSQL ended the statement itself. A later read leaves the session's `statement_timeout` unchanged.
- **Docs.** `backup-restore.md` describes the shared, bounded read, the `timeout` and `unavailable` reasons with their operator actions, the owner view's unreadable state and 0011's new checks.
- **Outside the write set.** The owner pool (`packages/web/src/server/owner/runtime.ts`) has no `connectionTimeoutMillis`. The recovery read no longer waits on it, but a connection the pool starts for that read can stay pending until the pool's own connect ends. Proposal: set `connectionTimeoutMillis` on that pool.

The container HEALTHCHECK and `container-smoke.mjs` are unchanged and still pass: a recovery `timeout` or `unavailable` makes only those checks `down` and the site `degraded`, answered with 200.

## 2026-11-26 — Fix round 2

The Codex re-review (blog-fab8) of `0061f79` said HOLD: one P1, two P2 and a nit, all confirmed by the coordinator. All four are fixed as uncommitted edits on `0061f79`, inside the admitted write set. Migration 0011 is unchanged in this round, and `packages/web/src/server/owner/runtime.ts` was not touched.

### 1. P1: at most one waiting pool checkout

- **Problem.** `latest()` raced `pool.connect()` against its deadline. pg-pool keeps a queued checkout, and the owner pool has no `connectionTimeoutMillis`, so each timed-out health request left one more waiter in the shared queue.
- **Design: one connection request per pool.** `postgres-operation-runs.ts` keeps a `WeakMap` from each pool to its one pending `pool.connect()` and a first-in, first-out list of the reads waiting for it.
  - Every store on the pool shares it. Each health request builds its own store, so the state cannot live in the store.
  - A read that finds a request in flight waits for it within its own deadline and never issues another. A read that gives up leaves the list.
  - When the request resolves, the connection goes to the oldest read still waiting, and a new request is made only while reads still wait. If no read waits, the connection goes back to the pool unused.
  - A failed request fails every read that waited for it; the next read asks again.
  - A read whose deadline fires just as its connection arrives hands the connection back without sending its statement.
- **Why this design.**
  - It holds the required property inside the write set, whatever the pool's own timeouts. pg-pool cannot withdraw a queued checkout, so the number of requests is the only thing this file can bound.
  - On a free pool, reads get connections one at a time. A health request makes one read, so this costs nothing measurable.
- **Not taken: failing fast when `waitingCount > 0`.** It would report a momentarily busy pool, such as a burst of owner requests, as `timeout`, so the checks would flap. It would also tie the store's port to a pg-pool counter. The one-request bound already limits the cost to one waiter.
- **Unit tests.**
  - **Saturated pool.** A real `pg` 8.22 `Pool` with `max: 1` and an in-process client through the pool's `Client` option, with its one connection held. Three concurrent reads, then three sequential reads, each through its own store, all reject with `TimeoutError`, and `waitingCount` stays at 1 throughout. After the holder releases, the queue drains to 0 and the connection is idle (released unused); a later read succeeds.
  - **Reuse.** On the same pool, a read that starts after the first timed out waits for the left-over request and gets its connection when the pool frees.
  - **Free pool and failures.** Three concurrent reads ask for connections one at a time. A failed request fails both reads waiting on it, and the next read asks again.
  - **The race.** A read whose caller gives up as its connection arrives hands it back unused, with no statement.
  - The earlier store tests (stalled request, stalled statement, caller abort, already aborted, `57014`) pass unchanged.
  - **Mutation check.** With one request per read restored, the saturated-pool tests fail with `waitingCount` 3, as the review measured.
- **Integration.** The held-lock test is unchanged.
- **Still proposed (outside the write set).** `connectionTimeoutMillis` on the owner pool would still help the owner pages' own requests. The health reads no longer depend on it.

### 2. P2: backup staleness follows the recoverable point

- **Order confirmed; no stop needed.**
  - `backup.mjs` takes `startedAt = now()` before it reads the key or calls `create`.
  - `createBackup` opens the snapshot in `capturePostgresSnapshot`. It records `snapshotAt` after `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, and PostgreSQL takes the snapshot at the first statement after that, `pg_export_snapshot()`.
  - So `startedAt` precedes the snapshot in real time, and the run's start bounds the snapshot's age from above. No schema change was needed.
- **Code.** `runAgeFrom` in `operation-runs.ts` counts a backup's age from `startedAt` and a drill's from `finishedAt`. `runAgeMs` uses it, so the stale finding, the health `ageMs` and the owner view's `ageMs` all follow it. The latest run is still chosen by `finished_at`, then id, and the drill's cadence is unchanged.
- **What each time shows.**
  - `/api/health`: `backup.ageMs` is the milliseconds since the latest backup started. `restoreDrill.ageMs` is the milliseconds since the latest drill finished.
  - `/owner/jobs`: "The last backup started at … and worked." When stale, it adds "but that is more than 24 hours ago." A failed backup still says when it stopped, and the drill card still says when it finished. The maintainer details keep both times.
- **Trade-off, documented.** This reverses "Age runs from finish, not start" under [Health check shape](#health-check-shape-decision). With one backup a day, the check is `stale` for about the run's length each day, because a restore in that window would lose more than 24 hours. The runbook says to start backups more often than every 24 hours, for example every 12 hours, or to let the alert tolerate the run time.

### 3. P2: `channel_binding=require` is enforced in node-postgres

- **Mechanism.** `drillPoolConfig` is split out of `drillPool`, which now builds its pool from it. For `require` it sets the Pool's `Client` option to `ChannelBindingClient`, a `pg.Client` subclass, and adds a pg-pool `onConnect` check. Every Node connection `drillPool` builds uses it, the recorder's included. `prefer` and `disable` keep the default client, as before.
- **The guard.** `requireChannelBinding` is the one function that touches pg internals. It wraps the client's `connection.emit`, through which pg 8.22 hands every backend message to the client's handlers, under its pg-protocol name.
  - A cleartext or MD5 password request is refused before the client fetches or sends a password.
  - A SASL request is refused unless the server offers SCRAM-SHA-256-PLUS and the stream is a TLS socket (`getPeerCertificate`). pg then chooses PLUS.
  - At SASLFinal, the guard reads `client.saslSession.mechanism` before pg checks the server's signature and clears the session.
  - AuthenticationOk is refused unless that mechanism was PLUS and pg cleared `saslSession`, meaning the server's signature checked out. This covers plain SCRAM, a server that lets the client in without asking, and a PLUS exchange the server does not finish.
  - A refusal emits one `ChannelBindingError` (a fixed message with no URL, host or driver text), destroys the socket, and drops every later message. The key data and ReadyForQuery that arrive in the same packet therefore never reach the client, so there is no second connect callback.
- **Backstop.** `onConnect` refuses any new client the guard did not mark as bound. A pg change that hid authentication from the guard therefore fails closed.
- **Mutation checks.** Without the subclass, the `require` tests fail. With the guard bypassed, the backstop still refuses every connection, and the tests catch the password that was sent.
- **Errors.** Callers keep their fixed codes. `backup:create` reports `operation_failed`. The recorder reports `operation_failed` too, which exits `3` when the set was kept.
- **Tests (`restore-drill-postgres.test.ts`).** An in-process fake PostgreSQL server sits behind a fake verified-TLS stream. The stream presents a DER certificate stub from which pg reads the SHA-256 signature hash. The server runs SCRAM in full against a password built at run time and checks the client's channel binding and proof. Through the pool `drillPoolConfig` builds:
  - only SCRAM-SHA-256 offered: refused under `require`, with no SASL answer sent, and accepted under `prefer`; `prefer` still binds when PLUS is offered;
  - SCRAM-SHA-256-PLUS: accepted under `require`, bound to the certificate's hash;
  - cleartext, MD5 or no authentication: refused, with no password sent;
  - an unfinished PLUS exchange, PLUS without TLS, or a forged server signature: no connection;
  - the recorder writes its run over a bound connection, and fails with `operation_failed` over an unbound one;
  - after a refusal, nothing the server sends reaches the client.
- **Pin test.** Against plain `pg.Client`, it fails if the internals change shape. It checks three things. The connection's listeners see the four SASL messages by name, before the client's handlers. `saslSession.mechanism` is PLUS at SASLContinue and SASLFinal, and the session is null at AuthenticationOk. `connection.stream` is the stream given.
- **Docs.** In `backup-restore.md`, the "node-postgres does not refuse" caveat is replaced by the enforcement and its fixed error; `prefer` is unchanged.
