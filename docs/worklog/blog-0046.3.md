## Health check shape (decision)

- **Two checks, `backup` and `restoreDrill`, not one.** The two have independent states, reasons and ages, and a monitor or the owner needs to tell "backup stale" from "drill overdue". A single `recovery` check would have to collapse both into one reason and one age.
- **The brief's "healthy" is the existing `up` status.** Every other check and the container smoke already use that vocabulary, so I did not add a seventh status.
- **Reasons are generic,** because the check name already says which subsystem: `never_run`, `last_run_failed`, `stale`, `targets_missed` (drill only). Precedence: a failed latest run first, then missed targets, then staleness.
  - `targets_missed` covers a failed drill whose first failure is `rpo_exceeded` or `rto_exceeded`. It also covers a passed drill whose recorded measurements exceed today's `recoveryTargets`.
  - A drill that failed earlier, for example on a row mismatch, is `last_run_failed`.
- **Body: status and reason, plus `ageMs` and the existing `durationMs`.** `ageMs` is milliseconds since the latest run finished. `durationMs` is the probe's own timing, kept on every configured check. Failure codes, timestamps, measurements and counts stay out; tests assert this.
- **Age runs from finish, not start.** Measured from start, a healthy daily backup would flap `stale` while its successor runs. The trade-off is that the snapshot can be up to one run's duration older than reported. It is documented with the alerting advice.
- **Drill cadence is 35 days** (`restoreDrillCadenceMs`): the runbook's monthly minimum plus slack for a drill that moves a few days. RPO is `recoveryTargets.rpoMilliseconds` (24 h).
- **Never `down` for the site.** The findings degrade the check. A read failure, for example before 0011 is applied, makes the check `down` (`unavailable` or `timeout`), but only the database takes the site down. The route keeps answering 200 for degraded.
- **The in-memory runtime reports both checks as `not_configured`.** A runtime that cannot be created reports them `down`, like its other dependent checks.
- **Container checks still pass, unchanged.** The HEALTHCHECK exits 0 on `r.ok`, and a degraded report is 200. `container-smoke.mjs` accepts `ok`/`degraded` with database `up`/`degraded`. A freshly migrated container with no recorded runs reports `degraded` (`never_run`) with database `up`, so both pass.

- **Deploy order.** `/owner/jobs` and the new checks read `operation_runs`, so apply migration 0011 with the release, as for earlier migrations. Until then the checks are `down`/`unavailable` (site degraded) and the jobs page cannot load its runs.
